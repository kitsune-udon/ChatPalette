Sandboxを閉じる前に結果を回収する。0.8.0の試験結果を回収した後もウィンドウが残り、続くZigランナーの起動と競合した。今回の試験用構成であることをホスト側のプロセス引数で照合して両方を閉じ、クライアント・サーバー・VMが残っていないことを確認した。保守中の旧ランナーとZigランナーに同じ排他用mutexと既存セッションの確認を追加し、別プロセスがmutexを所有している間は双方とも試験を起動しないことを確認した。

再確認では `wsb list --raw` が空のときも `WindowsSandboxServer.exe` が待機していた。双方のランナーは起動プログラム、クライアント、VMを検出する。待機サーバーがある状態から試験用Sandboxを1件起動し、`--smoke` の成功後、そのセッションが残っている間は旧・Zig両ランナーが次の起動を拒否した。起動構成とセッションIDを照合して試験用セッションを閉じ、クライアント・VMと公開CLIのセッション一覧が0件になった。共有mutexを保持した状態でも双方が起動を拒否した。証拠は `dist/migration/sandbox-guard/live-a2e29739041c/` の `results/result.json`、`session-guard.json`、`legacy-session-guard.json`、`cleanup.json`、`runner-mutex.json`。旧ランナーのVM不要試験80項目と、Zigツールの単体試験11件も成功した。

Windows Sandbox CLIが使えるときは、両ランナーが共有mutexを保持して `wsb list --raw` も確認する。専用GUIDで起動したウィンドウのない実Sandboxを両方が一覧から検出し、新しいクライアントを起動せず終了した。試験専用GUIDだけを停止した後、セッション・クライアント・VMは0件。証拠は `dist/migration/0.9.0-sandbox-alias/windowless-session-proof-445b4881dca4/` の `result.json` と `cleanup.json`。CLIの `start` 単独で試した構成では65秒以内にゲスト結果が届かなかったため、結果を得る試験の起動経路は既存の `.wsb` を使う。

空の状態からZig版のスモーク試験、修正したランナーを使う0.8.0のソース・ワーカー試験の順で実行し、どちらも終了0。実行構成が一致する試験用Sandboxをそれぞれ閉じ、各終了後にセッション、クライアント、VMがすべて0件だった。0.8.0側は移行後の文書を含む作業ツリーからの実行でソース検査に失敗したため、0.8.0の隔離コピーへランナーの修正だけを適用して再試験した。証拠は `dist/migration/0.9.0-sandbox-alias/authorized-sandbox-series-c981ed204786/` の `result.json`、`zig-cleanup.json`、`legacy-cleanup.json`、`legacy.log`。
